# 双 Zone 路由调研任务说明

## 1. 调研目标

为经典农场 V3 的下一阶段实现寻找可验证的理论和工程参照，重点回答：

1. Gate 如何根据玩家 ID 找到逻辑 Shard，再找到当前 Zone Owner？
2. ShardMap 应由谁生成、怎样发布，为什么普通请求不能每次访问 Coordinator？
3. Gate 缓存旧路由后怎样发现错误并安全重试？
4. 如何保证同一个 Shard 同一时刻最多只有一个写 Owner？
5. Shard 从 Zone A 切换到 Zone B 时，怎样避免旧 Owner 继续处理请求或落库？
6. 当前三周原型应实现哪些机制，哪些生产级能力只保留接口和说明？

## 2. 项目当前基础

本调研不是从零设计。当前代码已经存在：

- `server/internal/routing/routing.go`：4096 个逻辑 Shard、`RouteEntry`、`PREPARING/ACTIVE/UNASSIGNED`、Lease、`owner_epoch`、`route_version` 和 `NOT_OWNER`；
- `server/internal/routing/http.go`：Coordinator 兼容的路由查询接口；
- `server/internal/gateway/http_adapters.go`：Gate 查询 Owner 并向 Zone 转发命令；
- `server/cmd/coordinator/main.go`：单节点、进程内 ShardMap，目前全部指向 `zone-local`；
- `server/cmd/zone/handler.go`：Zone 接收 Gate 命令并传递 `owner_epoch`；
- MySQL Dirty 写回路径已经校验本地 `shard_fences`；
- 单 Zone 完整农场主闭环和 MySQL 恢复已有证据。

因此下一步的实际问题是：把固定的单 `zone-local` 扩展为两个真实 Zone，补齐 Gate 路由缓存、目标 Zone 身份、旧路由刷新和 Owner 切换证据。

## 3. 资料选择标准

优先选择满足以下条件的论文或成熟项目：

- 官方论文、官方工程文章、官方文档或官方仓库；
- 明确区分逻辑身份与物理节点；
- 包含 Shard/Actor 目录、Placement 或路由缓存；
- 讨论单 Owner、Lease、故障、迁移或缓存失效；
- 能映射到 `Gate -> ShardMap -> Zone Owner`，而非只介绍数据库水平分表；
- 对 Go 原型具有实现参考价值。

最终选择：

| 资料 | 主要研究问题 |
|---|---|
| Google Slicer | 控制面和数据面分离、Assignment 发布、强一致归属 |
| Meta Shard Manager | Shard 生命周期、主 Owner 迁移、客户端路由库 |
| Akka Cluster Sharding | ShardRegion、Coordinator、Lease 与单 Owner |
| Microsoft Orleans | Actor Directory、本地缓存、错误路由与恢复 |
| Dapr Actor Placement | Placement Table 的计算、版本和分发 |
| Proto.Actor / Proto.Cluster | Go Actor Identity Lookup、PID 缓存与重试 |
| Pitaya | Go 游戏服的 Frontend Gate、Backend 和自定义路由 |

## 4. 产出

- `01-论文与成熟项目解读.md`：逐项解释资料的机制、价值和局限；
- `02-经典农场可借鉴结论.md`：将资料映射到当前代码，给出双 Zone 实现边界和验收标准。

## 5. 文档边界

本目录是学习和选型参考，不是正式架构真相：

- 当前架构仍以 `docs/context/CURRENT.md` 和 `docs/architecture/stateful-zone-v3-architecture.md` 为准；
- 本调研不会自动改变 ADR、协议或数据模型；
- 外部系统的生产规模不能转化为本项目的性能声明；
- 只有经过项目负责人确认、写入当前架构或新 ADR 的结论才成为正式决策。

## 6. 一句话结论

经典农场不需要照搬任何一个框架。最合理的组合是：借 Slicer 的控制面/数据面分离、Meta 的 Shard 迁移接口、Akka 的 Lease 单 Owner、Orleans/Dapr 的本地路由缓存、Proto.Actor 的失效重试，以及 Pitaya 的 Gate 到后端转发方式，在现有 Go 代码上完成一个可解释、可测试的双 Zone 原型。
