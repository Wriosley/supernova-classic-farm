# 任务分配：V3 性能容量与压测路线

## 一句话问题

怎样把“3000 万 DAU”逐层换算成可检验的 WebSocket 连接、业务 QPS、Actor 内存、Dirty 写回和 MySQL 压力，并为当前 V3 原型设计一条不夸大结论的本地到云端压测路线？

## 当前背景

当前原型已经具备：

- Login、Gate、Zone 和单节点 Coordinator 兼容进程；
- Protobuf HTTP/WebSocket；
- Player Actor Mailbox；
- MySQL Player Checkpoint、Fence 和异步 Dirty 写回；
- `GET_PLAYER_SNAPSHOT`、`GET_SHOP`、`BUY_SEEDS`、`PLANT`；
- 固定点成长、成熟固化和重启恢复证据。

当前容量数字仍是规划假设，没有压测证明：

```text
3000 万 DAU
375 万正常峰值 WebSocket
450 万连接压力容量
约 500 万峰值驻留 Actor
约 6.94 万条/秒游戏消息
约 60 个 Zone 的压测前设计点
```

这些数字不是从零开始。历史 V2 文档已经按“每人每天 60 次外部交互”和逐场景峰值系数，推导出约 6.94 万峰值入口消息，并估算过 Actor、Journal、事件和 Zone 数量。本任务必须复用这份行为模型作为基线，而不是重新发明一套数字。

但历史推导中至少三项已经不能直接沿用：

- V1 曾假设单人农场走 HTTP、只有 20% 峰值在线玩家建立 WebSocket；V3 改为全部游戏命令使用长期 WebSocket，因此连接基线从 75 万变为 375 万；
- V2 使用同步 Journal 和异步 Snapshot 的写放大；V3 已改为内存 Actor 加异步 Dirty Checkpoint，必须重新计算 Dirty 合并率、检查点字节和 MySQL 写入；
- “约 60 个 Zone”来自 V2 的 Actor 内存和 Journal 吞吐预估，不能作为 V3 采购或能力结论。

因此本任务不是重复粗算，而是审计旧公式、保留仍成立的玩家行为假设、替换已经变化的 V3 数据路径，并把结果转成分层压测与证据计划。

## 决策目标

形成一份可以指导后续脚本、指标和答辩的压测方案，明确：

1. DAU 怎样转换为场景化负载，而不是直接等同 QPS；
2. Gate、Zone Actor、Dirty/MySQL 分别该测什么；
3. 哪些指标决定瓶颈归属；
4. 单机结果怎样计算安全容量，哪些结果不能外推；
5. 本地、单云机、分布式压测各自证明什么；
6. 上云选型需要等待哪些实测输入。

## 调研范围

- 登录与重连突发；
- 长连接与 30 秒心跳；
- 读写业务消息混合；
- Player Actor 驻留内存、Mailbox、GC 和调度；
- Dirty 合并率、检查点大小、批量写入、Fence/CAS；
- MySQL 延迟、锁、连接池和写入放大；
- 负载生成工具和分布式压测边界；
- Go pprof、运行时指标、应用指标和 MySQL 观测；
- 从单实例结果到部署容量的计算方法；
- 与 20 分钟答辩直接相关的图表和证据结构。

## 非目标

- 不声称当前原型已经承载 3000 万 DAU；
- 不直接购买或部署云资源；
- 不在本任务中编写正式压测脚本；
- 不选择全球多地域、多云或 Kubernetes 生产方案；
- 不把工具默认值、理论上限或厂商配额当作项目实测；
- 不恢复 V1/V2 架构。

## 独立证据轨道

### 轨道 A：负载模型与压测工具

研究：

- DAU、峰值在线、连接、心跳、命令 QPS、重连速率之间的换算；
- k6、Grafana k6 WebSocket、Artillery 或 Go 自定义负载器的适用边界；
- 开环/闭环模型、到达率、并发用户和协调遗漏；
- 本地与分布式负载生成器自身成为瓶颈的问题。

输出：`10-证据-负载模型与工具.md`

### 轨道 B：Go、Actor 与 Gate 观测

研究：

- Go runtime、pprof、GC、goroutine、堆、调度和阻塞指标；
- WebSocket 连接、收发队列、慢连接、消息大小、认证和重连指标；
- Actor 驻留数、Mailbox 深度、命令延迟和热点玩家指标；
- 如何从观测判断 CPU、内存、网络或锁竞争瓶颈。

输出：`11-证据-Go与Actor观测.md`

### 轨道 C：Dirty、MySQL 与云端压测边界

研究：

- 检查点大小、Dirty 合并、批大小、写延迟和连接池指标；
- MySQL Performance Schema、事务、锁、redo/binlog 和慢查询观测；
- 压测机与被测服务隔离、云网络和托管数据库对结果的影响；
- 上云前必须获得的 CPU、内存、网络、连接和磁盘实测输入。

输出：`12-证据-Dirty与MySQL云端边界.md`

## 来源计划

优先顺序：

1. Go 官方诊断、pprof 和运行时指标文档；
2. Grafana k6、Prometheus、MySQL 8.4 官方文档；
3. 主流云厂商关于负载均衡 WebSocket、监控和压测的官方文档；
4. 论文或权威工程资料用于解释开放/闭合负载模型和协调遗漏；
5. 二手文章只用于发现问题，不作为关键结论的唯一证据。

每个关键事实必须紧邻直接来源。项目推导必须标记为“推断”或“计算示例”。

## 最终交付

`20-调研结论.md` 必须包含：

1. 一句话结论；
2. 从 DAU 到各层负载的公式和示例；
3. 一张 Mermaid 分层压测图；
4. Gate、Actor、Dirty/MySQL 的指标与瓶颈判定；
5. 本地、单云机、分布式三阶段压测路线；
6. 容量计算、安全系数和停止条件；
7. 20 分钟答辩中可直接展示的证据清单；
8. 上云任务的输入条件和后续问题；
9. 官方来源索引。
