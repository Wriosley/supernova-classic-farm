# R3 玩家快照读路径压测报告

## 一、测试目标

本次测试用于建立当前本地原型的第一份可复现读路径性能基线，主要回答：

- 一个 Gate、两个 Zone 和 MySQL 同机运行时，玩家快照读取能达到多少吞吐量；
- 并发增加后，延迟和吞吐量如何变化；
- 当前实现是否存在明显的连接稳定性问题；
- 后续 Actor、Push 和 Dirty 写回测试应从哪里继续。

本次结果只代表当前机器上的单实例原型，不代表生产环境容量，也不能直接证明系统已经支持 3000 万 DAU。

## 二、测试环境与模型

测试机器为 `PHAINONYU-PC0`：

- 操作系统：Windows/amd64；
- Go 版本：1.26.4；
- 逻辑 CPU：8 核；
- 服务部署：Login、Gate、两个 Zone、Coordinator 和 MySQL 均运行在同一台机器；
- 启动模式：带 MySQL DSN 的双 Zone 模式。

`benchrunner` 创建或复用隔离的 `bench_` 测试账号。每个虚拟用户完成真实的 HTTP 注册或登录、CSRF、WebSocket Ticket 和 Protobuf WebSocket 鉴权流程，然后在同一条连接上以闭环方式反复调用 `GET_PLAYER_SNAPSHOT`。

闭环模型表示每个虚拟用户必须等待上一次请求返回后才发送下一次请求。它更接近普通玩家的交互方式，也能通过延迟上升和吞吐回落观察系统的饱和点。

每档测试参数：

- 预热时间：10 秒；
- 正式采样：60 秒；
- 单次操作超时：5 秒；
- 并发虚拟用户：1、10、25、50、100；
- 原始 JSON、CSV 和自动报告：本地 `benchmark/results/r3poolfix*_0803/`，该目录不提交到 Git。

## 三、实测结果

| 并发虚拟用户 |    成功 QPS |      P50 |       P95 |       P99 |       最大延迟 | 错误数 |
| -----: | --------: | -------: | --------: | --------: | ---------: | --: |
|      1 |  3,094.83 | 0.519 ms |  0.554 ms |  1.029 ms | 157.561 ms |   0 |
|     10 | 13,250.00 | 0.602 ms |  1.512 ms |  2.090 ms |  93.561 ms |   0 |
|     25 | 15,046.84 | 1.512 ms |  3.172 ms |  4.523 ms | 155.378 ms |   0 |
|     50 | 16,080.84 | 2.749 ms |  6.094 ms |  9.225 ms |  24.700 ms |   0 |
|    100 | 13,846.43 | 6.245 ms | 15.066 ms | 23.256 ms | 141.900 ms |   0 |

其中：

- QPS 表示每秒成功完成的玩家快照请求数；
- P50 表示 50% 的请求延迟不超过该值；
- P95 表示 95% 的请求延迟不超过该值；
- P99 表示 99% 的请求延迟不超过该值。

## 四、结论

本机吞吐量在 50 个虚拟用户时达到本轮最高值，约为 16,080.84 QPS，此时 P99 为 9.225 ms。

并发增加到 100 后：

- QPS 从约 16.1k 回落到约 13.8k；
- P99 从 9.225 ms 上升到 23.256 ms；
- 请求仍然保持零错误。

因此，50 并发是当前机器和当前只读场景下观察到的吞吐拐点。100 并发时系统仍可稳定响应，但继续增加并发已经不能提升吞吐量，反而增加了排队和延迟。

## 五、压测中发现并修复的问题

最初的 10 并发测试会重复出现 6 个 `SERVICE_UNAVAILABLE` 响应。通过 Gate 内部失败分类，问题被缩小到 Gate 调用 Zone 时的 HTTP 传输失败，而不是路由解析、Actor 业务处理或响应校验失败。

当时 Gate 使用 Go 默认 HTTP 连接池：

- 每个目标主机默认只保留 2 条空闲连接；
- Gate 客户端空闲连接超时为 90 秒；
- Zone 服务端会在空闲 30 秒后关闭连接。

这会让 Gate 在特定时序下复用已经被 Zone 关闭的连接。修正后：

- Gate 每个目标主机最多保留 64 条空闲连接；
- Gate 在空闲 20 秒后主动淘汰连接；
- Gate 会在 Zone 的 30 秒服务端超时之前回收连接。

修复后，1、10、25、50、100 五档测试全部零错误，Gate 的命令失败计数也保持为空。

压测工具本身也修复了一个错误放大问题：旧版本在某个虚拟用户连接失效后仍会继续写入，从而产生大量重复的本地连接错误。新版本会在该虚拟用户第一次失败时停止，并在每个并发档完成后立即保存结果。

## 六、结果边界

本次测试不能用于宣称生产吞吐量或 3000 万 DAU 支撑能力，原因包括：

- 压测客户端、Gate、两个 Zone 和 MySQL 全部运行在同一台 Windows 机器；
- 尚未记录测试期间的 CPU、内存、GC、网络和 MySQL 资源占用；
- 场景仅测试只读的 Actor 玩家快照；
- 尚未测试 Dirty 异步写回吞吐和延迟；
- 尚未测试 Push 端到端延迟和积压；
- 尚未测试大量长期 WebSocket 连接；
- 尚未包含多机网络延迟和真实生产基础设施开销。
