# Expansion, Drain and Blue-Green Exercise Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> `superpowers:verification-before-completion`. This phase integrates and
> validates Phases 01–09; do not add new ownership algorithms during the drill.

**Goal:** Demonstrate controlled 8→9 expansion, graceful Zone removal, abrupt
failure and blue-green Zone replacement with reproducible evidence and rollback.

## Global Constraints

- Current/Fence remain authority; Desired only schedules work.
- No bulk route recomputation or all-at-once migration.
- Normal drain is loss-minimizing; abrupt death retains ADR-0006 Dirty-window risk.
- No Actor prewarming.
- Stop immediately on Fence/RouteStore corruption or dual-owner evidence.
- Do not call a local kind result proof of 30-million DAU.

## Task 1: Add operational controls

**Files:**

- Create: `server/internal/coordinator/membership/drain_test.go`
- Add authenticated admin endpoints in Coordinator wiring

Operations:

```text
BeginZoneDrain(logical_zone_id, incarnation_id)
CancelZoneDrain(...)  // only before any task crosses Fence
GetZoneDrain(...)
```

- DRAINING removes Zone from Desired candidates but does not mark it DEAD.
- Planner creates DRAIN-priority tasks for its Current Shards.
- Cancel allowed only while every task is PLANNED/pre-Fence.
- Zone becomes removable only when Current ownership count and open tasks are 0.
- Admin calls require existing internal auth and explicit operator identity.

- [ ] Test drain/cancel rules, restart reconstruction from tasks/routes and
  zero-owner completion.

## Task 2: Add observability and safety assertions

**Files:**
- Create: `server/internal/coordinator/invariants/audit.go`
- Create: `server/internal/coordinator/invariants/audit_test.go`
- Add Coordinator diagnostics endpoints/metrics

Audit all 4096 Shards:

- exactly one durable Current row;
- ACTIVE Current owner/epoch agrees with Fence;
- PREPARING agrees with Progress;
- one open Task/Progress per Shard;
- Current owner is known or explicitly unavailable;
- Publisher map version never exceeds RouteStore.

Any violation blocks new scheduling and reports shard/reason without player
data. Audit is diagnostic/safety, not a replacement transaction.

## Task 3: Rehearse 8→9 expansion

Procedure:

1. Capture 8-Zone membership, Current, Fence, task/progress and SDK versions.
2. Scale StatefulSet 8→9.
3. Wait for ninth Zone HEALTHY.
4. Record pure Desired diff count/distribution.
5. Enable bounded REBALANCE worker.
6. Observe global/source/target limits and request retry behavior.
7. Wait until tasks complete and audit passes.
8. Restart Coordinator and one migrated Zone; verify stable Current.

Do not modify Shard logical IDs. Record exact moved count rather than claiming
the expected statistical fraction.

## Task 4: Rehearse graceful removal and rolling update

- Begin Drain for one Zone.
- Verify it receives no new Desired ownership.
- Wait for all Shards to migrate and Actor/Dirty drain to complete.
- Delete/scale down only after zero Current owners.
- For rolling update of the same StatefulSet ordinal, preserve logical ID and
  change incarnation; no rebalance should occur.
- Validate PodDisruptionBudget and readiness prevent premature traffic.

## Task 5: Rehearse abrupt failure

- Kill one owning Zone without preStop.
- Observe SUSPECT after evidence, then DEAD after accepted threshold.
- Verify affected Shards fail closed until Fence/TargetReady/ACTIVE completes.
- Confirm new epochs, lazy Actor Load limiter and documented Dirty-window risk.
- Inject Tcaplus outage during failover; assert no memory-only switch.

## Task 6: Rehearse blue-green pool replacement

```text
old pool: stable old logical IDs
new pool: new StatefulSet name -> new logical IDs
```

- Deploy new pool with zero Shards.
- Confirm HEALTHY candidates and compute Desired.
- Drain old pool gradually with bounded tasks.
- Stop on invariant/latency/error thresholds.
- Remove old pool only after zero ownership and no open Progress.
- Rollback before Fence cancels tasks; after Fence rollback means forward
  migration to a healthy target, never restoring old epoch.

## Final Completion Gate

- 8→9 moves only Desired differences.
- Graceful removal reaches zero ownership before Pod removal.
- Restart of the same logical Zone causes no rebalance.
- Abrupt failure advances Fence/epoch before new ACTIVE.
- Blue-green uses new IDs and bounded forward migration.
- Three Coordinator replicas retain one active mutator.
- SDK caches converge and ordinary hits do not query Coordinator.
- Cold Loads remain bounded.
- Evidence distinguishes measured, derived and assumed claims.

After this gate, freeze architecture diagrams, capacity assumptions, bottleneck
analysis and defense material. Do not keep changing routing mechanics unless a
measured failure requires a superseding ADR.
