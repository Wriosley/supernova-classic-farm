# 广播与业务解耦 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> `superpowers:subagent-driven-development` or `superpowers:executing-plans`.
> 本阶段只拆分广播职责，不实现持久化广播、离线消息或客户端自动重连。

**Goal:** 业务代码只报告领域状态变化；Player Actor 统一生成有序公开农场事件；独立 Dispatcher 负责查找在线接收者并通过 Gate 推送。

**Architecture:** 公开地块变化在 owner Actor mailbox 内转换为带 activation version 和 `farm_view_seq` 的 Patch。Patch 进入内存有界 Dispatcher，由 Dispatcher 查询在线访客、按 Gate 分组并投递。广播采用在线 best-effort；消息丢失后由客户端通过 sequence gap 拉完整快照恢复。

**Tech Stack:** Go、Player Actor、FarmViewPatch、Visit Registry、gRPC Gate Push。

## Global Constraints

- 广播失败不能回滚已经成功的业务。
- 不把广播消息持久化到 Tcaplus、Outbox 或其他数据库。
- 不保证离线访客重放历史广播。
- Patch 状态读取和 sequence 分配必须在 owner Actor mailbox 内完成。
- 业务代码不能查询访客、选择 Gate 或调用 Push。
- Dispatcher 不能在每次广播时创建无界 detached goroutine。
- FriendInteraction 修改 owner 状态后，必须先完成权威同步持久化，再发布广播。
- 客户端遇到 activation version 变化或 sequence gap 时必须拉完整快照。
- 本阶段不实现第 06 阶段的自动重连和可靠 Push 缓存。

## 1. 当前耦合

项目已经有：

```text
server/internal/farmview/broadcast.go
```

它已经负责：

- 查询在线访客；
- 将 owner 和 visitor 按 Gate 分组；
- 调用 Gate Push。

仍需拆分的部分：

- `player.Runtime` 根据 Action 判断哪些操作修改公开地块；
- `publicPlotIDsChanged` 是中央业务 Action switch；
- Runtime 直接调用 `notifyPublicPlots`；
- Runtime 负责启动广播 goroutine；
- `sync_persist` 保存广播专用的 `farmViewPlotIDs`；
- 新增地块业务时需要同时修改业务和 Runtime 广播判断。

目标改为：

```text
业务状态变化
-> DomainChanges
-> Actor生成FarmViewEvent
-> Dispatcher
-> Gate
-> 在线客户端
```

## 2. 职责边界

### 2.1 业务代码

业务代码只负责：

```text
修改了哪些地块
```

业务代码不负责：

- 是否存在访客；
- 接收者连接在哪个 Gate；
- 如何发送 gRPC；
- 广播超时；
- 广播重试；
- sequence gap 恢复。

### 2.2 Player Actor

Actor 负责：

- 在 mailbox 内收集领域变化；
- 去重并排序发生变化的 plot ID；
- 增加 `farm_view_seq`；
- 从当前权威 State 构造 FarmViewPatch；
- 将不可变事件交给 Dispatcher。

### 2.3 Dispatcher

Dispatcher 负责：

- 接收 FarmViewEvent；
- 查询当前在线 owner/visitor；
- 按 Gate 分组；
- 调用 Gate Push；
- 记录成功、失败、丢弃和队列深度；
- 在关闭时停止接收并有界排空。

### 2.4 客户端

客户端继续按以下规则处理：

```text
收到的 activation version != 本地 version
-> 拉完整快照

收到 seq == 本地 seq + 1
-> 应用 Patch

收到 seq <= 本地 seq
-> 视为重复或旧消息，忽略

收到 seq > 本地 seq + 1
-> 说明中间有消息丢失
-> 拉完整快照
```

## 3. 事件模型

建议新增内部类型：

```go
type DomainChanges struct {
    PlotIDs []uint32
}
```

要求：

- Plot ID 唯一；
- 按升序排列；
- 空集合不生成公开事件；
- 不包含 Gate、Visitor、Protobuf Envelope 或网络错误。

建议新增广播事件：

```go
type FarmViewEvent struct {
    OwnerPlayerID uint64
    Patch         *wsv1.FarmViewPatch
}
```

该事件必须在 Actor mailbox 内完整构造。

Dispatcher 收到后不得再次读取 Actor State。

具体类型名称可以按现有包结构调整，但职责边界不能改变。

## 7. 停止条件

出现以下情况时停止并重新检查设计：

- Patch 需要在 mailbox 外读取 Actor State；
- 业务 handler 仍需知道 Visitor 或 Gate；
- 广播失败会导致业务命令返回失败；
- 为解耦广播必须修改业务规则；
- Dispatcher 使用无界队列或每事件一个 goroutine；
- FriendInteraction 在 SaveCAS 前发送 owner Patch；
- 客户端无法检测 sequence gap；
- 必须持久化所有广播才能保证当前协议正确；
- 与其他好友任务发生不可安全合并的冲突。

## 8. 项目所有者复盘

完成后应能口述：

```text
业务代码只负责修改状态并报告哪些地块发生变化，不关心当前有没有访客，也不
知道访客在哪个 Gate。

Player Actor 在 mailbox 内根据领域变化增加 farm_view_seq，并从提交后的权威
状态生成不可变 Patch。Dispatcher 在 Actor 外查询在线接收者、按 Gate 分组并
推送，因此网络发送不会阻塞或回滚业务。

广播不持久化，只服务在线同步。如果客户端漏掉 seq=18，之后收到 seq=19，
它不能假设 19 包含 18 的变化，而是检测到序号缺口并拉完整快照。最终正确性
来自 Actor 权威状态和快照，不来自广播历史。
```

## 9. 决策状态

已经确认：

- 广播不持久化；
- 广播失败不影响业务成功；
- 丢广播使用 sequence gap 和完整快照恢复；
- 业务与接收者查询、Gate 分组和 Push 解耦；
- Patch 在 owner Actor mailbox 内生成；
- FriendInteraction 先完成权威持久化再广播。

仍为 `proposed`：

- `DomainChanges` 和 `FarmViewEvent` 的最终类型名称；
- Dispatcher 队列容量和 worker 数量；
- 队列满时选择丢弃最新事件还是标记接收者需要快照；
- Dispatcher Close 的最大排空时间；
- 指标使用现有日志还是新增 metrics 接口。
