# 3000 万 DAU 架构方案规划与未决问题收敛计划（V1 历史计划）

> 本计划基于无状态 V1，已停止执行。可复用的未决问题应重新放入 V2 的实施计划；AI 不得继续按本文的无状态 Zone 步骤推进。

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` when executing this plan task-by-task. All work items use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不推翻玩家分片混合架构主方向的前提下，把当前尚未闭环的正确性、容量、数据、容灾、安全、发布和验证问题逐项转化为可解释、可决策、可验证的方案。

**Architecture:** 继续采用“无状态 Zone + 玩家核心状态同分片 + MySQL 最终事实 + 可重建热点缓存 + 可靠事件 + HTTP 权威快照 + WebSocket 已提交变化推送”的主方向。本计划不预先接受具体中间件或实例数量，而是通过决策记录、缩小版原型、容量计算和故障证据逐项收敛。

**Tech Stack:** Go、Vue 3 H5、MySQL；Redis、Kafka/NATS JetStream/RabbitMQ 等仍为候选。

## 全局约束

- 生产目标是 3000 万 DAU；本地原型只验证机制和单实例基线，不能声称已经承载目标规模。
- 单地域、三个可用区是当前目标边界；全球多地域多活不在第一版范围内。
- 同一玩家的农场、资产、幂等结果和 Outbox 保持同分片本地事务。
- Redis 不能成为金币、仓库和地块的唯一事实。
- 跨玩家奖励、任务和邮件允许最终一致，但必须保证幂等、可追踪和最终可补偿。
- 三个客户端同时进入一个农场只是本地原型验收基线，不是生产产品硬上限；生产热点农场的连接、进入速率、快照 QPS 和广播上限由 A-04、B-11 与 E-08 收敛。
- 每个规划结论必须标注为“题目要求、设计决定、规划假设、候选方案或实测结论”之一。
- 本计划只负责收敛方案；具体实现仍按单人闭环、分片、异步、跨分片、实时和验证六阶段推进。

## 使用方法与完成标准

每个待办不是简单的“补一段文字”，而是应至少形成以下一种产物：

1. 产品语义决定：写入需求或架构文档；
2. 重大技术取舍：形成 proposed ADR，经项目负责人复述后再接受；
3. 容量问题：形成可复算的公式、参数来源和敏感性分析；
4. 正确性问题：形成状态机、时序图、唯一约束或自动化测试；
5. 可用性问题：形成故障假设、降级路径、恢复目标和故障实验；
6. 性能问题：形成压测脚本、原始结果、通过标准和局限说明。

优先级定义：

- **P0**：实现相应功能前必须决定，否则可能造成数据错误或整体返工；
- **P1**：进入分布式、好友或实时阶段前必须决定；
- **P2**：性能报告、答辩或生产化说明前必须完成。

## 工作流 A：产品边界与核心正确性（P0）

- [ ] **A-01 修正 HTTP 快照与 WebSocket 订阅之间的漏事件窗口。**
  - 设计方向：先完成 WebSocket 订阅登记并返回 Ack，H5 在浏览器内存缓存增量，再通过 HTTP 获取权威快照；以快照版本为基线丢弃旧事件并连续应用新事件。
  - 完成标准：定义订阅 Ack、权威快照版本、`base_version/version` 连续性、客户端临时缓存上限、超时、溢出、断线和 `resync_required`；用自动化时序测试覆盖版本 10→11 的竞态。Redis 可以加速经版本校验的快照，但不能作为防漏事件机制。

- [ ] **A-02 明确多人在同一农场中可以执行哪些操作。**
  - 解释：目前偷菜流程清楚，但“多人操作同一农场”可能被理解为访客也能种植、收获或铲除，业务边界不明确会改变权限和一致性设计。
  - 完成标准：列出主人、好友、普通访客的操作矩阵；明确第一版是否只是“同时观看 + 偷菜”，以及业务命令是否全部走 HTTP。

- [ ] **A-03 明确同一地块的并发冲突规则。**
  - 解释：两人同时偷、收获或操作同一地块时，只广播版本不能保证业务只成功一次。
  - 完成标准：选择行锁、条件更新或版本 CAS；定义成功者、失败错误码和客户端刷新行为；增加并发测试验证产出不会超发。

- [ ] **A-04 把“三人同时在线”固化为容量约束或明确仅为原型约束。**
  - 解释：广播扇出、热点农场和房间服务容量都依赖单农场同时在线上限。
  - 完成标准：明确生产目标是否也限制为三人；若不是，给出新的同时在线上限与热点保护模型。

- [ ] **A-05 决定生产注册初始化的对外语义。**
  - 解释：账号服务与玩家 Zone 分离后，账号、钱包、农场无法由一个数据库事务一次创建。
  - 完成标准：决定注册接口等待激活还是返回 `initializing`；定义重试、超时、永久失败、重复注册和未激活账号清理状态机。

- [ ] **A-06 将宠物能力纳入目标架构的数据归属。**
  - 解释：宠物属于开题基础要求，但当前生产目标服务边界中没有其状态归属。
  - 完成标准：决定宠物配置和玩家宠物状态分别由配置服务与 Zone/独立模块拥有；给出最小获得、列表和展示流程。

- [ ] **A-07 将图鉴能力纳入目标架构的数据归属。**
  - 解释：图鉴也是开题基础要求，适合由首次获得物品事件驱动，但尚未进入事件与分片模型。
  - 完成标准：定义按 `player_id` 保存的解锁记录、首次获得事件、幂等键和查询方式。

- [ ] **A-08 统一所有依赖时间的业务语义。**
  - 解释：成熟、邀请过期和每日任务都依赖时间；若依赖客户端时间或为每块地建立定时器，会产生作弊和海量定时器问题。
  - 完成标准：统一使用服务器绝对时间；定义存储时区、每日刷新时区、时钟偏差策略，并采用 `mature_at` 的惰性成熟判断。

- [ ] **A-09 建立玩家经济账务和对账策略。**
  - 解释：本地事务与幂等只能降低错误概率，无法自动发现遗漏、错误配置或人工操作造成的不一致。
  - 完成标准：定义资产流水、非负/上限约束、唯一奖励约束、周期性对账项、异常告警和补偿流程。

- [ ] **A-10 建立全领域数据所有权与分片键矩阵。**
  - 解释：农场、资产、宠物、图鉴、好友、任务、邮件、房间订阅和连接状态分散在不同段落，缺少一个可以检查重复写入和跨库调用的统一视图。
  - 完成标准：逐项列出最终事实所有者、主查询键、分片键、缓存、写入入口、一致性级别、保留期和禁止跨库修改规则；至少覆盖农场/地块、资产、账号、好友、任务、邮件、宠物、图鉴、房间订阅和 WebSocket 连接。

## 工作流 B：容量模型、流量与成本（P0/P1）

- [ ] **B-01 用业务脚本解释“每人每天 60 个 HTTP 请求”的来源。**
  - 解释：该数字目前只是聚合假设，无法证明能代表一小时在线游戏行为。
  - 完成标准：按四次登录分别列出进入农场、商店、种植、收获、好友、任务和邮件请求次数，并计算低、中、高三档请求量。

- [ ] **B-02 为不同流量类型设置独立峰值系数。**
  - 解释：在线人数、登录、写入、活动、邀请和任务刷新不一定同时按平均值的三倍变化。
  - 完成标准：分别给出登录、HTTP 读、HTTP 写、WebSocket、新建连接和消息事件的峰值假设及来源。

- [ ] **B-03 建立逐接口容量矩阵。**
  - 解释：只有总 QPS 无法定位是登录、读快照、交易还是好友访问成为瓶颈。
  - 完成标准：每个核心接口记录峰值 QPS、请求/响应大小、数据库读写数、缓存访问数、事件数和目标延迟。

- [ ] **B-04 计算服务内部调用、索引、复制和事件带来的放大。**
  - 解释：6.25 万外部 QPS 不等于数据库或消息系统的真实负载。
  - 完成标准：按实际事务 SQL、索引、binlog、副本、Outbox 和消费者写入重新计算全链路放大。

- [ ] **B-05 估算 WebSocket 业务消息与广播吞吐。**
  - 解释：连接数和心跳数不能代表地块变化、补发和多人广播产生的 CPU 与吞吐。
  - 完成标准：计算每秒业务事件、平均扇出、帧大小、序列化开销和单网关安全广播能力。

- [ ] **B-06 估算 API、WebSocket 和静态资源的网络带宽。**
  - 解释：出口带宽可能比应用 QPS 更早成为容量和成本瓶颈。
  - 完成标准：分别计算 HTTP、WebSocket Ping/Pong、业务推送、快照和 H5 静态资源的峰值入站/出站带宽。

- [ ] **B-07 建立单区故障后的重连风暴模型。**
  - 解释：一个区故障可能同时触发 TLS 握手、Session 校验、重新订阅和快照恢复。
  - 完成标准：估算断开连接数、抖动窗口、每秒握手数和各依赖的额外容量，并将其纳入 N+1 余量。

- [ ] **B-08 补充登录、每日刷新、活动和缓存冷启动等尖峰场景。**
  - 解释：日均和普通峰值不会覆盖同步发生的业务波峰。
  - 完成标准：列出至少零点刷新、热门活动、批量补偿邮件、版本发布和 Redis 重建五种尖峰，分别给出保护策略。

- [ ] **B-09 用注册用户、MAU 和留存估算长期规模。**
  - 解释：3000 万 DAU 只能描述当天负载，不能决定账号和长期玩家数据总量。
  - 完成标准：给出总注册用户、MAU、不活跃玩家比例和留存假设，并做敏感性分析。

- [ ] **B-10 重新计算所有在线与离线数据增长。**
  - 解释：当前历史估算只覆盖种植记录，遗漏资产流水、幂等、Outbox、任务、邮件、好友和运维数据。
  - 完成标准：按领域列出原始数据、索引、binlog、消息副本、备份、日志、指标、Trace 和冷归档的日增量与保留期。

- [ ] **B-11 建立热点与流量倾斜模型。**
  - 解释：平均分布会掩盖热门邀请、热点农场、热点缓存 Key、热点数据库分片和热点消息分区。
  - 完成标准：定义热点比例和最大单 Key/单农场负载；给出限流、隔离、请求合并和降级方案。

- [ ] **B-12 将 H5 静态资源与 CDN 纳入入口架构。**
  - 解释：美术、JS 和 CSS 流量可能远大于 API，不应由应用网关承担。
  - 完成标准：说明静态资源内容哈希、长期缓存、CDN 回源、版本对应和故障回退边界。

- [ ] **B-13 给出目标架构的粗粒度成本模型。**
  - 解释：技术可行不代表资源成本合理，三可用区、副本、缓存内存和网络都可能主导成本。
  - 完成标准：按 MySQL、缓存、消息、计算、带宽、日志和归档列出主要成本变量，不要求绑定具体云厂商价格。

## 工作流 C：分片、数据库与缓存（P0/P1）

- [ ] **C-01 设计逻辑分片在线迁移状态机。**
  - 解释：仅“复制后切换映射”无法保证迁移期间不重不漏。
  - 完成标准：定义准备、全量复制、增量同步、校验、切流、观察、清理和回滚状态，以及各状态允许的读写行为。

- [ ] **C-02 定义迁移期间幂等、Outbox 和事务的一致性。**
  - 解释：请求可能同时到达新旧库，Outbox 也可能被两个 Publisher 发送。
  - 完成标准：明确写入权威库、旧路由拒绝/重定向行为、幂等记录迁移和 Publisher 隔离规则。

- [ ] **C-03 设计分片路由配置的版本化与分发。**
  - 解释：Zone 缓存旧路由时可能把请求发送到已经迁走的数据库。
  - 完成标准：定义配置真相来源、版本号、缓存 TTL、变更通知、旧版本检测和紧急回滚。

- [ ] **C-04 确定账号服务的分片键和查询模式。**
  - 解释：登录可能按账号名、手机号摘要或外部身份查询，不能直接假设都按 `player_id`。
  - 完成标准：列出唯一键、分片键、全局索引需求、注册和登录读写路径。

- [ ] **C-05 确定好友关系的数据模型和分片方式。**
  - 解释：双向好友既要支持双方列表，也要快速判断两人是否为好友，单条或双写模型代价不同。
  - 完成标准：选择关系表示方式；定义创建、删除、重复接受、好友满额和部分失败的恢复语义。

- [ ] **C-06 确定任务、邮件和图鉴的分片键。**
  - 解释：这些服务虽然独立，但查询主要按玩家，批量系统任务/邮件又可能产生特殊写入模式。
  - 完成标准：说明玩家数据分片、批量创建策略、索引和归档方式。

- [ ] **C-07 规划 Zone 到物理分片的数据库连接模型。**
  - 解释：每个 Zone 若连接所有数据库，实例数乘以分片数会造成连接爆炸。
  - 完成标准：计算最大连接数；决定按需连接、连接池上限、空闲释放、代理需求和故障后的连接风暴保护。

- [ ] **C-08 规划核心大表的索引、时间分区和清理方式。**
  - 解释：历史、流水、幂等和 Outbox 会快速增长，大事务删除和错误索引会影响在线业务。
  - 完成标准：为核心访问模式列出索引；定义时间分区、批量清理、30 天归档和清理限速策略。

- [ ] **C-09 定义数据库在线 DDL 与兼容迁移策略。**
  - 解释：大表直接加索引或删除字段可能长时间锁表，且新旧服务版本会同时运行。
  - 完成标准：采用 expand→migrate→switch→contract 流程；明确回滚点和迁移进度监控。

- [ ] **C-10 定义 Cache Aside 的可见一致性。**
  - 解释：数据库提交后若缓存删除延迟，其他读请求仍可能看到旧值；版本字段本身不能自动消除旧值。
  - 完成标准：定义读己之写、写接口返回状态、最大旧值窗口、版本化回填和缓存失效失败处理。

- [ ] **C-11 设计缓存击穿、雪崩与恢复后的重建策略。**
  - 解释：热点 Key 失效或 Redis 恢复会让大量请求同时回源 MySQL。
  - 完成标准：明确 TTL 抖动、单 Key 请求合并、回源限速、分批预热和数据库保护阈值。

- [ ] **C-12 定义 Redis 故障时的限流退化方式。**
  - 解释：限流状态丢失时直接放行会放大故障，所有限流都回源数据库又会拖垮事实库。
  - 完成标准：决定本地保守限流、核心白名单、非核心功能关闭和恢复后的计数重建策略。

- [ ] **C-13 设计 API Gateway、玩家路由与 Zone 的请求边界。**
  - 解释：当前只有高层拓扑，尚未说明调用者 A、目标玩家 B、业务授权和分片路由分别由谁验证，旧路由或错误重试可能把请求送到错误分片。
  - 完成标准：定义 Session 得到的可信 `caller_player_id`、请求携带的 `target_player_id/farm_id`、网关鉴权与限流、Zone 业务授权、目标玩家逻辑分片计算、`route_epoch` 校验、可信元数据传播、超时重试和错误返回；明确 API Gateway 不执行好友或农场业务规则。

## 工作流 D：可靠事件与跨服务一致性（P0/P1）

- [ ] **D-01 完整定义 `request_id` 幂等契约。**
  - 解释：同一 ID 如果被用于不同接口或不同参数，简单返回旧结果会造成错误业务结果。
  - 完成标准：绑定玩家、操作类型和请求摘要；定义唯一约束、处理中/成功/失败状态、保留期和清理方式。

- [ ] **D-02 保证消费者去重记录与业务更新同事务。**
  - 解释：先更新业务再记录去重，或反过来分两次提交，都会在崩溃窗口中产生重复或遗漏。
  - 完成标准：为任务、奖励、偷菜和邮件领取分别定义 Inbox/唯一键事务模板，并用崩溃重试测试验证。

- [ ] **D-03 设计 Outbox Publisher 并发抢占和发送状态机。**
  - 解释：多个 Publisher 可能重复发送，同一玩家事件也可能乱序。
  - 完成标准：选择 `SKIP LOCKED`、租约或 CDC；定义待发送、发送中、已发送和失败状态，以及超时接管行为。

- [ ] **D-04 定义 Outbox 顺序、保留和清理规则。**
  - 解释：Outbox 无限增长会拖慢扫描；过早删除又会丢失审计和补发能力。
  - 完成标准：明确需要有序的事件范围、发送确认、分区索引、在线保留期和归档/删除批次。

- [ ] **D-05 设计消息重试、毒消息和死信处理。**
  - 解释：永久失败的消息可能一直阻塞一个分区，导致后续玩家事件无法处理。
  - 完成标准：区分可重试与永久错误；定义退避、最大次数、死信、告警、人工修复和重新投递流程。

- [ ] **D-06 定义事件标识、Schema 版本和兼容规则。**
  - 解释：发布后仍可能消费或重放旧事件，新旧消费者必须能够共存。
  - 完成标准：事件统一包含 `event_id`、类型、Schema 版本、发生时间和业务 Key；建立向后兼容规则和契约测试。

- [ ] **D-07 决定历史事件重放时使用哪个业务配置版本。**
  - 解释：旧收获事件套用新任务或新价格配置可能发出错误奖励。
  - 完成标准：决定事件携带配置版本或不可变计算结果；定义旧配置保留与重放语义。

- [ ] **D-08 明确跨分片偷菜的好友授权一致性。**
  - 解释：持有地块锁时同步调用好友服务会延长事务，使用缓存又可能短暂允许已删除好友。
  - 完成标准：选择事务前校验、短期授权凭证或授权投影；明确允许的撤权延迟和失败行为。

- [ ] **D-09 完善满仓奖励转邮件的异常状态和对账。**
  - 解释：从仓库入账转为邮件需要跨服务，任何中间崩溃都可能让奖励长期停留在 `mail_pending`。
  - 完成标准：定义状态机、唯一键、重试、超时扫描和“仓库或邮件恰好一个最终去向”的对账规则。

- [ ] **D-10 定义任务事件的顺序、重复与配置切换语义。**
  - 解释：任务进度可能收到乱序、重复或跨版本事件，单纯累加可能多发奖励。
  - 完成标准：定义按玩家/任务的顺序需求、去重键、完成状态唯一约束和配置版本切换点。

- [ ] **D-11 定义消费者去重记录的保留、重放与清理边界。**
  - 解释：Inbox 记录若早于消息保留期或人工重放窗口删除，旧事件可能再次产生业务效果；永久保留又会让去重表无限增长。
  - 完成标准：规定临时去重保留期不短于消息保留期、最大重试时间和允许重放窗口之和；区分可清理 Inbox 与必须留在资产流水、奖励、偷菜或邮件业务表中的永久唯一事实；定义时间分区、限速清理和清理后重放行为。

## 工作流 E：实时连接与房间服务（P0/P1）

- [ ] **E-01 设计房间服务的生产分片方式。**
  - 解释：原型单 Room Service 不能直接外推到 75 万连接，订阅路由自身需要水平扩展。
  - 完成标准：确定按 `farm_id` 分片或其他路由；说明实例发现、迁移和容量计算。

- [ ] **E-02 设计同一农场跨多个实时网关的广播。**
  - 解释：同一房间的连接可能分散在多个网关，房间服务必须找到全部目标且允许重复但不能静默漏发。
  - 完成标准：定义网关订阅登记、广播消息、幂等/版本处理和网关确认边界。

- [ ] **E-03 定义网关故障后的陈旧订阅清理和恢复。**
  - 解释：网关突然退出后，房间服务可能继续向不存在的网关发送消息。
  - 完成标准：使用租约、心跳或注册会话识别陈旧订阅；定义重新连接后的订阅重建流程。

- [ ] **E-04 定义断线增量的保留和补发窗口。**
  - 解释：`last_seen_version` 只有在服务端保留相应增量时才能补发。
  - 完成标准：确定保留位置、时长、最大条数和超限后强制拉快照的规则。

- [ ] **E-05 定义 WebSocket 鉴权、续期和撤销。**
  - 解释：长连接建立后 Session 可能过期、被撤销或因单设备登录而失效。
  - 完成标准：明确握手 Token 传递、Origin 校验、定期续期、踢线通知和每条命令的授权边界。

- [ ] **E-06 定义慢客户端的发送队列与断开协议。**
  - 解释：无限队列会耗尽网关内存，随意丢消息又可能造成客户端无感知地停留在旧版本。
  - 完成标准：确定队列字节/条数上限、可合并事件、不可丢事件、关闭码和重连后的强制恢复行为。

- [ ] **E-07 设计心跳定时器、抖动和负载均衡空闲超时。**
  - 解释：大量连接同时建立可能形成同步心跳波峰，错误超时参数还会导致周期性断线。
  - 完成标准：定义心跳随机抖动、Ping/Pong 超时、定时轮或等效低成本实现，并与 LB 空闲超时对齐。

- [ ] **E-08 设计热点农场的房间限额与隔离。**
  - 解释：热门邀请或异常流量可能让单个 `farm_id` 压垮一个房间分片、消息分区或缓存 Key。
  - 完成标准：定义同时连接、进入速率、快照 QPS 和广播频率上限，以及超过后的拒绝/降级表现。

## 工作流 F：高可用、灾难恢复与过载保护（P0/P1）

- [ ] **F-01 给出 MySQL 分片在三个可用区的副本拓扑。**
  - 解释：无状态计算 N+1 不能替代事实库的副本和选主设计。
  - 完成标准：标出主副本分布、复制模式、写确认条件、故障检测和切换责任组件。

- [ ] **F-02 设计 MySQL 选主隔离和防脑裂机制。**
  - 解释：旧主未被隔离时，新旧主可能同时接受写入，`request_id` 无法修复两个事实源。
  - 完成标准：定义仲裁、Fencing、旧主隔离、DNS/路由切换和复制落后副本禁止提升规则。

- [ ] **F-03 验证 RPO 接近 0 与写延迟目标是否兼容。**
  - 解释：更强的同步复制通常意味着更高跨区写延迟，目标不能只写理想结果。
  - 完成标准：比较异步、半同步和同步复制；记录延迟、数据风险和最终选择。

- [ ] **F-04 给出 Redis、消息、Session 和路由配置的多可用区拓扑。**
  - 解释：这些组件任一成为单点都会使整体三可用区目标失效。
  - 完成标准：分别为消息系统、Redis、Session 真相源和分片路由配置列出副本分布、选主/仲裁、写确认、网络分区行为、单区丢失后的可写性、允许的数据损失、降级路径、恢复步骤和故障实验；不能用同一套“主从”描述替代四种不同语义。

- [ ] **F-05 设计单地域灾难的备份与恢复方案。**
  - 解释：副本不能防止误删和全地域故障，错误数据也会复制到全部副本。
  - 完成标准：定义全量/增量备份、时间点恢复、异地保存、保留期、恢复目标和定期恢复演练。

- [ ] **F-06 定义各服务过载时的功能优先级。**
  - 解释：过载时如果所有功能一起排队，核心资产操作也会被非核心查询拖垮。
  - 完成标准：明确登录/资产、农场读、好友、实时、任务、归档的优先级和逐级关闭顺序。

- [ ] **F-07 为关键依赖设置熔断、超时和隔离预算。**
  - 解释：一个下游变慢会耗尽上游连接、线程或 Goroutine，引发级联故障。
  - 完成标准：为数据库、缓存、好友、消息和配置调用定义超时、连接池、并发上限、熔断和重试预算。

- [ ] **F-08 建立完整故障矩阵。**
  - 解释：当前故障实验覆盖单进程和部分中间件，但未覆盖网络分区、复制延迟、磁盘满、路由错误等情况。
  - 完成标准：按实例、进程、节点、可用区、网络、磁盘、配置和人为错误列出影响、自动处理、人工步骤和验证实验。

- [ ] **F-09 设计 API Gateway 与 Realtime Gateway 的三可用区部署和切流。**
  - 解释：无状态网关也会持有连接、发送队列和短期路由状态，单区故障会触发 HTTP 切流和 WebSocket 重连风暴。
  - 完成标准：定义三区实例分布、负载均衡健康检查、停止接流、连接排水、单区摘除、重连抖动、订阅重建、N+1 容量和切流期间的请求/连接恢复语义。

## 工作流 G：安全、反作弊与平滑发布（P1）

- [ ] **G-01 完成账号登录与 Session 安全设计。**
  - 解释：账号服务边界已经存在，但密码哈希、失败限速、Cookie/Token 和撤销策略未定义。
  - 完成标准：明确密码哈希参数、登录限速、账号枚举保护、Session 有效期、撤销和单设备会话语义。

- [ ] **G-02 完成 H5、HTTP 与 WebSocket 的浏览器安全设计。**
  - 解释：Cookie 可能受 CSRF，Token 可能泄漏，WebSocket 也需要 Origin 和消息限制。
  - 完成标准：定义 HTTPS、CORS、CSRF、Cookie 属性、WebSocket Origin、消息大小和每连接速率限制。

- [ ] **G-03 完成分享邀请的安全与防滥用设计。**
  - 解释：可猜测或无限使用的邀请链接会造成批量刷好友和热点攻击。
  - 完成标准：定义 Token 随机强度、过期、最大使用、重复点击、自邀请、好友满额、创建/接受限速和审计。

- [ ] **G-04 建立服务器权威与反作弊约束。**
  - 解释：客户端时间、价格、成熟状态、奖励数量和好友身份都不能被信任。
  - 完成标准：列出所有服务端校验、非法状态跳转、操作频率、机器人行为信号和审计字段。

- [ ] **G-05 规划入口层 DDoS、WAF 和共享 NAT 保护。**
  - 解释：应用网关限流不能替代边缘防护，单纯按 IP 又会误伤大量共享网络用户。
  - 完成标准：说明 CDN/LB/WAF/网关的分层责任，以及 IP、账号、玩家、邀请和农场组合限流。

- [ ] **G-06 定义敏感数据、密钥、日志和备份保护。**
  - 解释：Token、密码、密钥和玩家数据一旦进入仓库或日志会形成长期泄漏风险。
  - 完成标准：明确 Secret 管理、日志脱敏、传输/备份加密、访问控制和数据删除边界。

- [ ] **G-07 设计 WebSocket 滚动发布和连接排水。**
  - 解释：直接终止网关会制造大量同时重连，破坏“平滑更新”目标。
  - 完成标准：定义停止接新连接、负载均衡摘除、旧连接排水、客户端抖动迁移和超时关闭流程。

- [ ] **G-08 定义 HTTP、事件和数据库的多版本兼容窗口。**
  - 解释：H5、新旧服务和滞留消息不可能在同一瞬间全部升级。
  - 完成标准：明确客户端最低版本、DTO 兼容、事件兼容和 expand→contract 数据迁移窗口。

- [ ] **G-09 建立配置灰度、功能开关和回滚策略。**
  - 解释：错误作物、任务或奖励配置可能比代码故障影响更快，必须可以限制影响面。
  - 完成标准：支持按玩家灰度、版本锁定、紧急停用、配置回滚和发布审计。

## 工作流 H：SLO、可观测性、压测与证据（P2）

- [ ] **H-01 为 99.95% HTTP、99.9% 实时和奖励到账目标定义 SLI。**
  - 解释：必须先定义什么请求、什么延迟和什么错误算失败，才能计算可用性。
  - 完成标准：确定成功条件、延迟阈值、排除项、统计窗口和数据来源。

- [ ] **H-02 建立错误预算和依赖预算。**
  - 解释：月度可用性目标需要在发布、数据库故障、单区故障和外部网络等风险之间分配。
  - 完成标准：计算月度允许失败时间，并为核心 HTTP、实时和异步奖励分别分配预算与冻结发布条件。

- [ ] **H-03 把监控指标转化为告警阈值和运行手册。**
  - 解释：只采集指标不能指导故障处理，需要明确何时告警以及采取什么动作。
  - 完成标准：为数据库、缓存、Outbox、Consumer Lag、奖励延迟、连接和重连设置阈值、负责人和处理步骤。

- [ ] **H-04 统一请求、事件和奖励的追踪标识。**
  - 解释：没有跨 HTTP、Outbox、消息和消费者的关联 ID，就无法解释奖励为什么延迟或重复。
  - 完成标准：规定 `trace_id/request_id/event_id/reward_id/theft_id/claim_id` 的生成、传播、日志和查询方式。

- [ ] **H-05 控制指标标签高基数和敏感信息。**
  - 解释：把玩家、农场或请求 ID 放入指标标签会拖垮监控系统，并可能泄漏敏感数据。
  - 完成标准：定义指标、日志、Trace 和审计数据各自允许的字段、采样和保留期。

- [ ] **H-06 使用开放负载模型执行 HTTP 压测。**
  - 解释：固定并发会在服务变慢时自动降低发压速率，从而掩盖过载。
  - 完成标准：按目标到达率持续发压，记录排队、拒绝、吞吐和延迟崩溃点。

- [ ] **H-07 避免延迟统计中的 Coordinated Omission。**
  - 解释：服务卡顿时压测端若暂停发送，报告会漏掉本应到达的慢请求。
  - 完成标准：验证工具按计划发送时间计算延迟，并保留直方图或原始延迟分布。

- [ ] **H-08 分别测试均匀、热点、冷缓存和恢复流量。**
  - 解释：平均负载通过不能证明热点 Key、热点分片和 Redis 恢复时安全。
  - 完成标准：至少建立均匀玩家、热点农场、热门邀请、冷缓存和 Redis 重建五套场景。

- [ ] **H-09 在目标负载下执行故障实验。**
  - 解释：空载停进程只证明基本切换，不能证明故障时剩余容量和恢复路径有效。
  - 完成标准：在 HTTP、消息和 WebSocket 负载下分别停止 Zone、消费者、网关、Redis 和数据库主节点并记录影响。

- [ ] **H-10 执行长时间稳定性测试。**
  - 解释：内存、Goroutine、连接、幂等表和 Lag 的缓慢增长无法由短压测发现。
  - 完成标准：设置数小时以上 soak test；记录资源趋势、泄漏、表增长和吞吐稳定性。

- [ ] **H-11 验证消息积压追平不会伤害在线业务。**
  - 解释：消费者恢复后全速追赶可能耗尽数据库连接和 CPU，使核心接口不可用。
  - 完成标准：记录积压产生、最大量、追平速率、追平时间和追平期间核心 HTTP p99；必要时实现消费限速。

- [ ] **H-12 为每项压测和故障实验预先定义通过标准。**
  - 解释：只记录 QPS 和 p99 容易事后挑选漂亮数字，不能判断方案是否达标。
  - 完成标准：每项实验在执行前写明目标负载、成功率、p99、资源安全线、恢复时间和允许的数据错误数。

- [ ] **H-13 在性能测试中同时验证业务不变量。**
  - 解释：高吞吐但金币、奖励或地块状态错误不能算通过。
  - 完成标准：自动核对金币守恒、奖励唯一、作物不可重复收获、偷菜不超发、版本单调和邮件附件只领取一次。

- [ ] **H-14 明确本地基线外推的限制和修正方法。**
  - 解释：本地没有跨区延迟、真实数据规模、复制和分布式协调开销，不能简单按实例数线性相乘。
  - 完成标准：报告中列出不可证明事项；按 CPU、数据库、缓存、消息、带宽分别外推并加入单区故障及发布余量。

## 阶段退出条件

只有同时满足以下条件，才可以把本计划视为完成：

- 所有 P0 项已经形成明确决定、状态机或测试，不再依赖口头假设；
- 所有 P1 项已经进入架构文档或 proposed/accepted ADR，并有验证安排；
- 容量模型可以从业务脚本重新计算出 HTTP、数据库、消息、WebSocket、存储和带宽负载；
- 单实例基线、故障实验和业务不变量结果已写入 `docs/evidence/`；
- 所有目标值、规划值和实测值均能明确区分；
- 项目负责人能够解释每项关键取舍的替代方案、代价和验证方式。
