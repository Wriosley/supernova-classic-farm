# ADR-0001：第一版采用模块化单体

## 背景

经典农场由一人独立开发，第一版只需在本机支持十几个玩家，但最终范围包含账号、农场、仓库、商店、任务、好友、宠物、图鉴、邮件和多人同步。购买、种植、收获、出售和奖励领取都涉及多个业务模块的强一致写入。

需要决定第一版是按功能拆成多个独立服务，还是在一个 Go 应用中保持模块边界。

## 考虑过的方案

### 方案 A：每个功能独立服务

优点：可以独立部署和扩容，物理边界清楚。

代价：立即引入网络失败、服务治理、日志追踪和跨服务一致性。购买需要同时扣金币和增加种子，收获需要同时清空地块和增加作物，邮件领取需要同时修改领取状态和发放奖励；拆服务后不能直接使用一个本地数据库事务。

### 方案 B：无边界的单体

优点：开发和部署最简单。

代价：模块任意跨表修改，测试和演进困难，未来拆分成本不可控。

### 方案 C：模块化单体

一个 Go 应用和一个 MySQL 实例，按业务模块组织包、领域服务、数据归属和测试。强一致业务共享短小的本地事务，模块之间通过明确能力协作，不允许 Handler 或其他模块任意改表。

## 决定

第一版采用方案 C：模块化单体。

- 账号、农场、仓库/资产、商店、任务、好友、宠物、图鉴和邮件保持独立代码模块；
- 第一版共同部署在一个 Go 进程中，使用同一个 MySQL 实例；
- 每张业务表有唯一负责模块，跨模块写入通过领域服务能力和显式事务编排；
- 事务中不调用外部网络服务；
- 多人阶段先在同一应用内增加 WebSocket 连接和房间能力；
- 只有压测、故障隔离、独立部署或团队边界提供证据时，才拆成独立服务。

## 理由

- 当前没有独立扩容或部署需求；
- 单人开发需要优先完成可运行闭环；
- 核心资产操作需要强一致，本地事务最容易实现和验证；
- 模块独立测试不要求物理服务拆分；
- 保持清晰模块边界后，未来仍可基于证据拆分，并比较拆分前后的性能和复杂度。

## 后果与风险

- 所有模块共同部署，不能独立扩容；
- 单进程故障影响全部功能；
- 共享数据库可能诱发跨模块改表；
- 本地事务使部分模块存在实现耦合。

控制方式：模块拥有自己的表和不变量；其他模块只能通过接口协作；为模块写独立单元测试，为购买、种植、收获、出售和领奖写跨模块事务测试。

## 验证方法

1. 静态检查项目包结构和模块依赖方向；
2. 每个模块具备独立领域测试；
3. 跨模块事务在中途失败时整体回滚；
4. 建立单实例功能和性能基线；
5. 只有监控或压测显示独立扩容、故障隔离或部署收益时，新增 ADR 讨论拆分。

## 重新评估条件

- 某模块资源需求与其他模块显著不同并成为已测瓶颈；
- 故障隔离成为明确要求；
- 需要独立发布节奏或不同团队负责；
- 单库事务或共享部署阻碍目标容量；
- 引入跨区域或多游戏复用需求。
