# ADR-0002：生产目标采用玩家分片混合架构

## 背景

ADR-0001 为独立开发和本地闭环选择了模块化单体。导师反馈要求方案从一开始说明如何支撑 3000 万 DAU，并通过缩小版分布式原型验证关键机制。原总体设计只给出“压测后再拆分”的演进方向，缺少目标服务边界、分片、缓存、消息、实时连接和容灾设计。

需要区分“最早可运行实现”和“生产目标架构”，同时避免为追求微服务数量而拆散强一致玩家数据。

## 考虑过的方案

### 方案 A：水平扩容模块化大服务

多个相同 Go 应用实例访问缓存和数据库分片。实现简单，但连接、核心交易、好友和异步任务共同扩容，故障与发布影响范围过大。

### 方案 B：每个业务模块独立服务

账号、农场、资产、商店、任务、好友、邮件和实时全部物理拆分。独立扩容清晰，但购买、收获、任务奖励和偷菜立即产生过多跨服务一致性问题，对当前独立开发和原型验证过重。

### 方案 C：玩家 Zone 分片为核心的混合架构

同一玩家的农场、资产、幂等和 Outbox 共同位于玩家分片，由无状态 Zone 处理；账号、好友、任务、邮件、实时连接和归档按流量与一致性特征独立。跨玩家与非核心流程使用 Outbox、可靠消息和幂等消费者。

## 决定

生产目标采用方案 C。

- 单地域三个可用区；
- 网关鉴权后按 `player_id` 路由；
- 无状态 Zone 处理玩家核心操作；
- 1024 个逻辑玩家分片映射到可扩展物理 MySQL 集群；
- MySQL 是核心状态最终事实，热点缓存只做可重建加速；
- 单玩家购买、种植、收获和出售使用本地事务，并在事务内写 Outbox；
- 任务进度和奖励异步处理，任务故障不回滚核心操作；
- 跨分片偷菜先提交农场主事实，再可靠异步投递好友奖励；满仓转不自动过期的系统邮件；
- HTTP 用于命令和快照，WebSocket 用于已提交变化的实时广播；
- 普通玩家最多 200 名好友；
- 最近 30 天历史在线保留，更早数据异步归档；
- 本地原型按核心事务、分片、消息、跨分片奖励、实时同步、证据与修订六阶段验证。

ADR-0001 不删除：它仍描述最早单进程业务闭环和代码模块边界。它不再代表 3000 万 DAU 的生产目标；本 ADR 在生产目标层面取代其“只根据未来证据再考虑分布式”的表述。

Redis、Kafka 等具体中间件产品尚未接受。当前只接受“可重建热点缓存”和“可保留、可重放、支持独立消费组的可靠事件系统”这两个能力需求；具体产品通过比较和原型证据另行决定。

## 理由

- 强一致玩家数据共同分片，保留简单可靠的本地事务；
- Zone 无状态，实例故障、扩容和滚动发布不需要迁移进程内玩家状态；
- 好友图关系、长连接和异步任务具有不同资源模型，可以独立扩容和降级；
- 逻辑分片提供稳定路由和物理数据库扩容路径；
- Outbox 与幂等消费者处理数据库成功、消息失败和重复投递；
- 双层架构既能说明生产容量，又能在本机验证关键机制。

## 后果与风险

- 任务进度和跨玩家奖励改为最终一致，客户端需要展示同步中/待到账状态；
- 消息、分片路由、缓存失效、邮件兜底和版本恢复显著增加实现复杂度；
- 跨分片流程不能假装拥有单库原子事务；
- 1024 逻辑分片、容量数字和实例规划都是待验证假设；
- 中间件故障、积压、重放和分区扩展需要监控与演练；
- 分布式原型范围必须严格分阶段，避免同时开发所有生产组件。

## 验证方法

1. 两个无状态 Zone 处理相同玩家，路由到相同数据库分片；
2. 停止一个 Zone 后，相同 `request_id` 重试不重复修改资产；
3. 停止任务消费者后核心操作继续，恢复后进度和奖励追平且只生效一次；
4. 农场主和好友位于不同分片时，偷菜奖励最终进入仓库或系统邮件；
5. 两个实时网关上的三个客户端通过版本同步，消息缺口用 HTTP 快照恢复；
6. 分别记录 HTTP、消息和 WebSocket 单实例基线，并用安全容量而非极限容量外推；
7. 故障实验和限制写入 `docs/evidence/`，不得把目标值表述为已达成。

## 重新评估条件

- 玩家单体状态或同玩家并发使无状态 Zone 的数据库往返成为已测瓶颈；
- 好友关系或热点农场无法通过缓存、限流和房间分片控制；
- 任务或奖励延迟不能满足产品体验；
- 逻辑分片迁移成本超过收益；
- 中间件原型显示运维复杂度或性能不满足目标；
- 部署地域扩展到多地域多活。
